# foreman 需求文档

> 最后更新：2026-09-09
> 模块：core
> 状态：Phase 1 定稿（基于 2026-09-09 的 grill 决策树，共 40 项已拍板决策）

## 一、产品背景与目标

### 1.1 产品定位

foreman 是一个**单人使用**的 AI 协作平台，以"任务"为一等公民，把分散在飞书、Jira、GitHub 里的需求，和分散在笔记本、中心机、开发机上的 Claude Code / Codex 会话，串成一条可追踪、可拍板、可逐步自动化的流水线。

一句话：**需求进来自动变成带上下文的任务，agent 在合适的机器上接手，人只在需要拍板的地方出现，拍板多了就不再需要人。**

### 1.2 核心目标

| 目标 | 度量指标 | 第一版目标值 |
|------|---------|-------------|
| 需求零遗漏 | 分配给我的 Jira 单与打了表情的飞书消息，未进入任务系统的数量 | 0 |
| Agent 一键接手 | 从需求入库到分流卡出现在收件箱的时间 | ≤ 10 分钟（含开发机预跑代码定位） |
| 减少决策疲劳 | 每天需要我手动确认的动作数 | 随信任升级逐周下降，可在面板看到趋势 |
| 交付尾巴不丢 | 我的 open PR 中未被平台追踪的数量 | 0（M2） |
| 会话可找回 | 平台派发的会话中，无法回答"它在解决哪个任务"的数量 | 0 |

### 1.3 目标用户画像

姜凯，SelectDB 的 Apache Doris 内核工程师（GitHub `airborne12`），倒排索引方向。日常：

- apache/doris 上约 650 个历史 PR，同时保持约 20 个 open PR；内部仓 selectdb-core 需要把同一修复 pick 到多个分支族。
- 需求来源：飞书群里 @他、飞书私聊、Jira（SelectDB 自建 Server，项目 CIR，需 VPN）、GitHub PR 的 review 意见。
- 工具：Claude Code 与 Codex 交叉使用（开发与 review 互换），均为月订阅，明确不走 API 计费；偶尔用 OpenCode。
- 机器：笔记本（macOS）、中心机 172.17.2.13（Mac M4 Pro，常驻）、开发机 10.26.20.3（CentOS 9，192 核，所有 Doris 克隆与构建环境在此）。
- 已有自动化：开发机上的 jira-watch、pr-fleet-watch、pr-watch、pick-pr、teamcity 等 skill，由 crontab 驱动，简报推飞书，状态散落在 `~/.local/state/`。

## 二、用户痛点分析

### P01: 需求入口分散，容易遗忘

因为需求同时来自飞书群、飞书私聊、Jira 和 GitHub → 导致没有一个地方能看到"所有待办需求" → 造成需求被遗漏，或者记得有事但找不到原始上下文。

### P02: Agent 无法一键接手需求

因为需求的上下文（对话前后文、Jira 字段、相关代码位置、目标仓库）散落各处 → 导致每次让 agent 干活都要人工搬运上下文、指定仓库和分支 → 造成简单需求也要花几分钟启动，很多小问题干脆积压不做。

### P03: 交付尾巴的心智负担

因为一个修复要经历 master PR、多个分支 pick、每个 PR 的 CI 与 review、逐个合入 → 导致要同时记住十几个 PR 各自到了哪一步 → 造成漏 pick、漏回复 review、pick 时文本合并干净但语义错误没被发现。

### P04: 多 Agent 工具的上下文碎片化

因为 Claude Code、Codex 各自维护 session，session 挂在工具和目录上而不是挂在任务上 → 导致频繁在工具间切换、忘记某个 session 在解决什么 → 造成重复劳动，或者半途而废的会话被遗忘。

### P05: 人在回路要么太累要么不敢放手

因为现有自动化要么每一步都问（飞书表情逐条审批），要么完全不问 → 导致要么决策疲劳，要么不敢开自动化 → 造成自动化的收益被"确认"这个动作吃掉。

### P06: 运行环境分散且能力不同

因为编译验证只能在开发机做、轻量分析在笔记本或中心机就够、笔记本会合盖 → 导致每次都要人工决定"在哪台机器上跑"并手动 ssh 过去 → 造成任务卡在错误的机器上，或者笔记本一合盖任务就断。

### P07: 现有自动化碎片化

因为 jira-watch、pr-fleet-watch 等各自维护状态文件、各自的 cron、各自的飞书简报，且每轮都要起一个 `claude --print` 进程 → 导致没有统一的任务状态，轮询类的确定性工作也在烧订阅额度 → 造成简报之间互相不知道对方，同一个 PR 的信息要在多份简报里拼。

### 场景粒度自检

- 单 API 测试：每个场景都跨越"外部事件 → 平台处理 → agent 或人参与 → 状态回写"多个环节，无单 API 场景。
- CRUD 测试：没有以"创建任务 / 查询任务 / 更新任务 / 删除任务"划分的场景，任务的增删改都内嵌在业务路径里。
- 业务价值测试：每个场景的价值都写在"用户价值"一栏，均为用户可感知的结果而非数据读写。
- 步骤数测试：所有场景主路径 ≥ 3 步。

## 四、核心场景详述

### 术语

- **任务（Task）**：树形结构。根任务对应一条需求；子任务对应一个 PR 或一个目标分支；子任务下挂事件（CI、review、pick）。
- **上下文包（Context Pack）**：需求原文、来源对话前后文、Jira 字段、目标仓库、相关代码定位、预估工作量。
- **分流卡（Triage Card）**：agent 对一条新任务的第一份产出：档位（简单修复 / 出方案 / 出原型）、预估工作量、目标仓库、建议路径。
- **Runtime**：一台被 worker 管理的机器，声明能力标签（可编译 doris、有 selectdb-core 克隆、装了 claude / codex 等）。
- **动作类型**：需要人确认的动作的分类，用于信任升级计数。清单：分流卡确认、启动实现、创建 PR、发起 pick、解冲突并推分支、回复 review 意见、重跑 CI、合入 master、合入 release 分支（永远人工）、Jira 流转到处理中、Jira 完成（永远人工）、飞书回帖。
- **审批（Approval）**：一条待人确认的记录，绑定任务、动作类型和正文哈希，面板与飞书表情等价，先到先得，用过即失效。
- **频道 / 线程**：IM 中由用户自建的频道；每个根任务在其频道内是一条线程，子任务和事件是线程内消息。
- **调度员会话**：每个频道按需拉起的一个 agent 会话（订阅 CLI），负责把口语解析成结构化任务，空闲后回收。

### S01: Jira 单自动入库并生成分流卡

- **触发条件**：Jira 中有 issue 的 assignee 变为我（含新建即分配和后来改派）
- **用户价值**：不用再自己盯 Jira，分配给我的单会带着上下文和初步判断出现在收件箱（← P01, P02, P07）
- **优先级**：P0
- **主路径**：平台在具备 VPN 能力的 runtime 上轮询 Jira → 发现新分配的 issue → 创建根任务并落到 Jira 来源的默认频道 → 组装上下文包（issue 字段、评论、附件摘要、按 Jira 项目/组件映射目标仓库）→ 在开发机上以"分析类"任务预跑代码定位 → agent 产出分流卡 → 分流卡进入待拍板收件箱，并推一条飞书私聊

#### 验收条件

##### 正常：新分配的 CIR 单在 10 分钟内出现分流卡
- **GIVEN** 平台正常运行，开发机 runtime 在线，Jira 项目 CIR 已配置到 selectdb-core 仓库的映射
- **WHEN** Jira 上 CIR-20001 的 assignee 被改为我
- **THEN** 10 分钟内收件箱出现 CIR-20001 的分流卡，卡片包含档位、工作量预估、目标仓库 selectdb-core、建议路径与代码定位摘要；飞书私聊收到一条"待拍板"消息，消息含面板链接

##### 正常：重复分配不重复建任务
- **GIVEN** CIR-20001 已存在对应任务
- **WHEN** Jira 上 CIR-20001 被改派给他人再改回我
- **THEN** 不创建新任务，原任务线程追加一条"重新分配"事件

##### 异常：无法推断目标仓库
- **GIVEN** Jira 项目 DORIS 没有配置仓库映射，issue 正文也没提到仓库
- **WHEN** DORIS-300 被分配给我
- **THEN** 任务仍然创建，分流卡的目标仓库标为"待确认"并给出 LLM 猜测的候选，收件箱条目要求我先选仓库

##### 异常：开发机离线，预跑无法进行
- **GIVEN** 开发机 runtime 心跳超时
- **WHEN** 新 issue 被分配给我
- **THEN** 任务创建，分流卡以"无代码定位"的降级形式出现，卡片标注"开发机离线，代码定位待补"，开发机恢复后自动补跑并更新卡片

##### 异常：Jira 不可达
- **GIVEN** 所有能访问 Jira 的 runtime 都离线，或 VPN 断开
- **WHEN** 到达轮询时刻
- **THEN** 平台记录一次"来源不可达"事件，面板状态视图显示 Jira 来源为红色，恢复后的第一次轮询以上次成功的水位线为准补齐事件，不丢单

### S02: 飞书消息显式入库

- **触发条件**：我在飞书给某条消息加上固定表情（默认 📌），或在群里 @平台机器人
- **用户价值**：群里、私聊里的口头需求一个动作就进系统，不用复制粘贴（← P01, P02）
- **优先级**：P0
- **主路径**：平台以机器人身份订阅飞书事件 → 收到表情或 @ 事件 → 拉取该消息及其前后若干条对话 → 创建根任务并落到飞书来源的默认频道 → 组装上下文包（LLM 猜测目标仓库）→ 预跑代码定位 → 分流卡进收件箱，并在原消息下回一条"已收录"

#### 验收条件

##### 正常：群消息打表情入库
- **GIVEN** 平台机器人已加入该群，我在群里
- **WHEN** 我给同事的一条消息加上 📌
- **THEN** 5 秒内该消息下出现机器人回复"已收录为任务 T-xxx"，收件箱随后出现分流卡，上下文包含该消息前后各 20 条对话

##### 正常：@机器人直接派活
- **GIVEN** 平台机器人已加入该群
- **WHEN** 我在群里发"@foreman 把这个查询超时的问题看一下"并引用一条消息
- **THEN** 以被引用消息为需求原文、我的话为补充说明创建任务，后续同"打表情入库"

##### 异常：别人打的表情不入库
- **GIVEN** 平台只认我的 open_id
- **WHEN** 同事给一条消息加上 📌
- **THEN** 不创建任务，不回复

##### 异常：同一消息重复打表情
- **GIVEN** 某消息已入库为 T-100
- **WHEN** 我取消再重新加 📌
- **THEN** 不创建新任务，机器人回复"已存在 T-100"

##### 异常：LLM 扫描出的候选不打扰
- **GIVEN** 平台开启了候选扫描
- **WHEN** 我的私聊里出现一条疑似需求但我没打表情
- **THEN** 它只出现在面板的"候选"列表，不推飞书，不建任务；我在面板一键确认后才走入库流程

### S03: 拍板分流路径并一键启动 agent

- **触发条件**：收件箱里有一张分流卡等待确认
- **用户价值**：看一眼卡片、点一次按钮，agent 就在正确的机器上带着完整上下文开始干活（← P02, P05, P06）
- **优先级**：P0
- **主路径**：我在收件箱（或飞书表情）选择路径：简单修复 / 出方案 / 出原型，可改目标仓库与档位 → 平台按任务类型和能力标签选择 runtime（代码相关一律开发机）→ 按策略选 agent（开发 agent 轮换）→ worker 创建 worktree，写入上下文包 markdown，通过 MCP 暴露任务接口 → 以 `claude --bg` 或 `codex exec` 启动会话 → 会话进展摘要写入任务线程 → 产物：方案文档、demo 分支加一页说明、或修复分支加 PR → 产物摘要单向镜像回来源（Jira 评论 / 飞书回帖）

#### 验收条件

##### 正常：简单修复路径直到 PR
- **GIVEN** CIR-20001 的分流卡档位为"简单修复"，目标仓库 selectdb-core，开发机在线且有 claude 与 codex
- **WHEN** 我点击"按建议执行"
- **THEN** 60 秒内开发机上出现该任务的 worktree 与一个后台会话；线程里出现"已启动，runtime=开发机，agent=claude"；会话结束后线程出现 PR 链接，任务树下新增该 PR 子任务；Jira 单收到一条带 PR 链接的评论（该动作受信任升级约束）

##### 正常：出方案路径
- **GIVEN** 分流卡档位为"出方案"
- **WHEN** 我确认
- **THEN** 会话在开发机上产出一份方案 markdown，线程展示全文，收件箱出现"方案待拍板"条目，我可以选择"按方案实现"直接进入实现路径，不必重新描述需求

##### 正常：agent 轮换与交叉 review
- **GIVEN** 上一个实现任务由 claude 开发
- **WHEN** 新任务启动实现
- **THEN** 本次开发 agent 为 codex；实现完成后自动创建的 review 子任务由 claude 执行，且线程中标明两者

##### 异常：路由目标离线
- **GIVEN** 开发机离线
- **WHEN** 我确认一个代码相关任务
- **THEN** 任务进入队列，线程显示"等待开发机上线"，不会退回笔记本或中心机执行；开发机上线后自动启动

##### 异常：agent 并发已满
- **GIVEN** claude 在开发机已有 3 个运行中会话
- **WHEN** 新任务需要 claude
- **THEN** 任务排队，线程显示队列位置；若任务类型为"分析类"且 codex 有空位，则改派 codex 并在线程说明

##### 异常：会话失败
- **GIVEN** 会话运行中
- **WHEN** `claude agents --json` 报告该会话 state 为 failed
- **THEN** 线程显示失败原因摘要与日志入口，收件箱出现"重试 / 换 agent / 放弃"三选一的条目，worktree 保留

##### 异常：worktree 回收
- **GIVEN** 任务到达终态已超过 3 天，或开发机磁盘使用率超过 85%
- **WHEN** worker 执行回收
- **THEN** 终态超 3 天的 worktree 被删除；磁盘超阈值时从最老的终态 worktree 开始删，运行中的任务不受影响，删除记录写入任务线程

### S04: 在 IM 频道用口语派活

- **触发条件**：我在自建的频道里输入一句话
- **用户价值**：不用填表单、不用记命令，像跟同事说话一样派活，平台把它变成结构化任务（← P02, P04）
- **优先级**：P0
- **主路径**：我新建频道（如 `#doris-index`）→ 在频道里输入"把 CIR-19418 修了，顺便 pick 到 branch-selectdb-doris-3.1" → 平台按需拉起该频道的调度员会话 → 调度员通过 MCP 读取相关 Jira / PR 信息，生成任务草案（目标仓库、路径、pick 目标）→ 草案以卡片形式回到频道 → 我确认或修改 → 任务创建为该频道下的线程，进入 S03 流程

#### 验收条件

##### 正常：一句话变成带 pick 目标的任务
- **GIVEN** 频道 `#doris-index` 存在，CIR-19418 可通过 Jira 读取
- **WHEN** 我输入上述句子
- **THEN** 30 秒内频道出现任务草案卡片：需求来源 CIR-19418、目标仓库 selectdb-core、路径"简单修复"、pick 目标 branch-selectdb-doris-3.1；我点"创建"后频道出现新线程，收件箱出现分流卡

##### 正常：斜杠命令兜底
- **GIVEN** 调度员会话不可用（额度耗尽或 CLI 故障）
- **WHEN** 我输入 `/task new --source CIR-19418 --repo selectdb-core --path fix`
- **THEN** 不经 LLM 直接创建任务草案卡片，其余流程相同

##### 正常：调度员会话回收
- **GIVEN** 频道的调度员会话已空闲 30 分钟
- **WHEN** 回收时刻到达
- **THEN** 会话被停止，下次频道有输入时重新拉起，频道历史作为上下文重新提供

##### 异常：语义不明确
- **GIVEN** 我输入"看看那个索引的问题"
- **WHEN** 调度员无法确定指哪条需求
- **THEN** 频道内回复澄清问题并列出最近相关的候选任务或 Jira 单，不创建任务

##### 异常：一句话对应多个任务
- **GIVEN** 我输入"CIR-19418 和 CIR-19420 都修一下"
- **WHEN** 调度员解析
- **THEN** 生成两张草案卡片，各自独立确认

### S05: 接入一台 runtime 并让任务路由到它

- **触发条件**：我在一台新机器上安装 worker，或已有机器重启
- **用户价值**：机器的能力和连接方式配置一次，之后任务自动去该去的地方，笔记本合盖不影响（← P06）
- **优先级**：P0
- **主路径**：我在机器上安装 worker 并填写配置（中心地址、预共享 token、能力标签、仓库克隆路径、构建环境变量、传输方式）→ worker 拨中心并注册 → 面板状态视图出现该 runtime 与标签 → 心跳维持 → 新任务按"任务类型默认需求 + 标签匹配 + 手动覆盖"路由

#### 验收条件

##### 正常：开发机通过反向隧道接入
- **GIVEN** 开发机无法主动连到中心机，中心机可 ssh 到开发机
- **WHEN** 中心机建立 `ssh -R` 反向隧道并启动开发机 worker
- **THEN** worker 通过 localhost 隧道端口注册成功，面板显示 runtime "dev-192core" 在线，标签含 `build:doris`、`repo:selectdb-core`、`agent:claude`、`agent:codex`

##### 正常：笔记本直连接入
- **GIVEN** 笔记本能直连中心机
- **WHEN** 笔记本 worker 启动
- **THEN** 直接注册成功，标签含 `agent:claude`、`agent:codex`，不含 `build:doris`

##### 正常：按类型路由
- **GIVEN** 三台 runtime 在线
- **WHEN** 分别创建一个"代码修复"任务和一个"文本调研"任务
- **THEN** 前者路由到开发机，后者路由到中心机；线程里显示路由依据

##### 正常：手动覆盖
- **GIVEN** 任务默认路由到中心机
- **WHEN** 我在分流卡上把 runtime 改为开发机
- **THEN** 任务在开发机执行，覆盖记录写入线程

##### 异常：心跳超时
- **GIVEN** 开发机 worker 连续 3 次心跳（默认 30 秒一次）未到
- **WHEN** 中心判定离线
- **THEN** 面板标红，其上运行中的任务状态标为"失联"，不自动改派；恢复后 worker 上报会话真实状态并同步

##### 异常：token 错误
- **GIVEN** worker 配置了错误的预共享 token
- **WHEN** worker 注册
- **THEN** 中心拒绝并记录来源，worker 本地日志给出明确错误，不进入重试风暴（退避至少 60 秒）

### S06: 审批双通道与信任升级

- **触发条件**：平台产生一条需要人确认的动作
- **用户价值**：在电脑上批面板、在手机上点表情都行；确认得多了平台自动接管，出错一次立刻收回（← P05）
- **优先级**：P0
- **主路径**：平台生成审批记录（任务、动作类型、正文哈希）→ 同时出现在收件箱与飞书私聊 → 我在任一通道确认或否决 → 另一通道同步失效 → 动作执行 → 该动作类型计数更新 → 连续 5 次原样确认后，该类型后续动作自动执行并在线程标注"自动（信任等级）"→ 任何一次否决或事后回滚清零计数并恢复人工

#### 验收条件

##### 正常：飞书先批，面板同步
- **GIVEN** 一条"回复 review 意见"的审批同时在收件箱和飞书
- **WHEN** 我在飞书点 ✅
- **THEN** 5 秒内收件箱该条目消失并显示"已在飞书批准"，动作执行，线程记录审批号与通道

##### 正常：五次后自动
- **GIVEN** "重跑 CI" 已连续 5 次被我原样确认
- **WHEN** 第 6 次需要重跑 CI
- **THEN** 不生成审批，直接执行，线程标注"自动执行，信任计数 5/5"，面板信任视图显示该类型为"自动"

##### 正常：否决清零
- **GIVEN** "回复 review 意见" 已处于自动状态
- **WHEN** 我在线程里对某次自动回复点"否决并回滚"
- **THEN** 平台撤回该回复（若来源系统支持），该类型计数清零，恢复为人工确认，面板显示降级记录

##### 异常：永远人工的动作不升级
- **GIVEN** "合入 release 分支" 已被我确认 10 次
- **WHEN** 第 11 次触发
- **THEN** 仍然生成审批，面板该类型显示"锁定人工"

##### 异常：正文变更导致审批失效
- **GIVEN** 一条审批已推到飞书
- **WHEN** 在我批准前 agent 修改了正文
- **THEN** 原审批作废并在两个通道标注"内容已变更"，生成新审批

##### 异常：修改后确认不计数
- **GIVEN** 一条审批
- **WHEN** 我修改了正文再确认
- **THEN** 动作按修改后内容执行，但计数不增加（"原样确认"才计数）

### S07: 跟踪会话进展并在线程中介入

- **触发条件**：某个任务的 agent 会话运行中，或会话需要输入
- **用户价值**：不用切到终端就知道 agent 干到哪了，需要我时一句话就能续上（← P04）
- **优先级**：P0
- **主路径**：会话通过 MCP 回写进展摘要 → 线程按摘要展示，可展开查看原始日志 → 会话 waitingFor 变为需要输入时，线程与飞书出现"需要你回答"→ 我在线程里回复 → 平台以"追加消息"动作（`--bg --resume` / `codex exec resume`）把回复送入会话 → 会话继续

#### 验收条件

##### 正常：摘要与日志
- **GIVEN** 一个运行中的 claude 会话
- **WHEN** 我打开任务线程
- **THEN** 线程按时间显示 agent 回写的进展摘要（每条 ≤ 200 字），每条可展开对应时间段的原始日志（来自 `claude logs`）

##### 正常：回答 agent 的问题
- **GIVEN** 会话报告 `agent_needs_input`
- **WHEN** 我在线程回复"用方案二"
- **THEN** 10 秒内回复被追加进该会话，会话状态回到运行中，线程显示"已送入会话"

##### 正常：完成通知
- **GIVEN** 会话运行中
- **WHEN** Notification 钩子报告 `agent_completed`
- **THEN** 线程出现完成摘要与产物列表，任务或子任务状态更新；若产生需确认动作则进入 S06

##### 异常：会话已被 supervisor 停止
- **GIVEN** 会话完成后闲置超过一小时，进程已被停止
- **WHEN** 我在线程追加消息
- **THEN** 平台用 resume 重新拉起同一会话 ID，线程显示"已恢复会话"，上下文不丢

##### 异常：在错误 runtime 上追加
- **GIVEN** 会话属于开发机
- **WHEN** 开发机离线时我追加消息
- **THEN** 消息排队并显示"等待开发机上线后送入"，不会在其他机器新开会话

### S08: PR 的 CI 失败与 review 意见闭环

- **触发条件**：我的 PR 收到 CI 结果或 review 评论
- **用户价值**：CI 失败和 review 意见自动归到对应任务，agent 先分类和处理，我只看需要拍板的（← P03, P07）
- **优先级**：P1
- **主路径**：平台轮询 GitHub 与 TeamCity → 事件挂到 PR 子任务 → CI 失败由 agent 判定"与本 PR 相关 / 环境不稳定"→ 相关则启动修复会话，不稳定则申请重跑（受信任升级）→ review 意见由 agent 分类"必须修 / 建议修 / 可忽略"并给出草案回复 → 必须修的启动修复，回复走审批 → 修复推送后重跑 CI，线程记录闭环

#### 验收条件

##### 正常：review 意见闭环
- **GIVEN** PR apache/doris#67657 是任务 T-200 的子任务
- **WHEN** reviewer 留下 3 条行内意见
- **THEN** 10 分钟内线程出现 3 条分类结果和回复草案，"必须修"的那条已启动修复会话；回复动作进入审批

##### 正常：CI 不稳定重跑
- **GIVEN** TeamCity 某次构建失败，失败用例与本 PR 改动无关
- **WHEN** agent 判定为不稳定
- **THEN** 生成"重跑 CI"审批（或自动执行），线程附判定依据

##### 异常：判定为相关但修复失败
- **GIVEN** 修复会话结束但 CI 再次失败
- **WHEN** 连续 2 次修复未通过
- **THEN** 停止自动修复，收件箱出现"需要你介入"条目，附两次失败的对比摘要

##### 异常：不是我的 PR
- **GIVEN** 轮询结果含他人的 PR
- **WHEN** 平台处理事件
- **THEN** 忽略并在状态视图记录一次配置告警，不创建任务

### S09: 指定分支 pick 与冲突处理

- **触发条件**：我在线程或频道里指定 PR、目标仓库与目标分支
- **用户价值**：pick 的机械部分自动做，冲突先给我分析和方案，语义风险永远标红（← P03）
- **优先级**：P1
- **主路径**：我指定"pick #66877 到 selectdb-core branch-selectdb-doris-3.1"→ 每个目标分支生成一个子任务 → agent 在开发机 worktree 里执行 pick（复用 pick-pr 能力）→ 无冲突：编译、测试、建 pick PR → 有冲突：只读试算后出"冲突分析与建议方案"进审批 → 我确认后解冲突并推分支、建 PR → 语义冲突风险（文本干净但涉及重构、函数移位）永远在线程标红提示

#### 验收条件

##### 正常：干净 pick
- **GIVEN** 源 PR 已合入，目标分支无冲突
- **WHEN** 我下达 pick 指令
- **THEN** 子任务创建，开发机上完成 pick 与编译，pick PR 创建并链接到线程；"发起 pick" 与 "创建 PR" 动作按信任等级处理

##### 正常：有冲突先给方案
- **GIVEN** 目标分支有文本冲突
- **WHEN** agent 试算发现冲突
- **THEN** 不改动分支；线程出现冲突文件清单、每个文件的冲突类型和建议解法；收件箱出现"按方案解冲突"审批；确认后才解冲突并推送

##### 异常：语义风险标红
- **GIVEN** 文本合并干净，但源改动涉及的函数在目标分支已被重构
- **WHEN** agent 完成 pick
- **THEN** 线程出现红色"语义风险"提示与具体位置，该 pick PR 的"合入"动作强制人工，不受信任升级影响

##### 异常：已存在 pick
- **GIVEN** 目标分支已包含该改动（按标题核心或 merge-base 判定）
- **WHEN** 我下达 pick 指令
- **THEN** 不建 worktree，线程回复"已存在"并给出证据

### S10: 合入与来源系统闭环

- **触发条件**：某个 PR 的 CI 全绿且 review 通过
- **用户价值**：合入这一步只需要点一次，之后 Jira、飞书自动闭环，任务自然到达终态（← P03, P05）
- **优先级**：P1
- **主路径**：平台判定 PR 具备合入条件 → 生成"合入"审批（master 可升级为自动，release 永远人工）→ 我确认 → 合入 → 子任务完成 → 全部子任务完成后，根任务执行闭环动作：Jira 流转（"处理中"可升级，"完成"永远人工）、飞书回帖摘要 → 根任务到达终态

#### 验收条件

##### 正常：master 合入与闭环
- **GIVEN** 任务 T-200 只有一个 master PR，CI 全绿，已 approve
- **WHEN** 我确认合入
- **THEN** PR 合入，子任务完成，收件箱出现"Jira 完成"审批；确认后 Jira 单流转到完成并附合入链接，飞书原消息（若来源是飞书）收到回帖，任务终态

##### 正常：多分支全部合入才终态
- **GIVEN** T-200 有 master PR 和两个 pick PR
- **WHEN** 只有 master PR 合入
- **THEN** 根任务保持进行中，线程显示"2 个 pick 待合入"

##### 异常：release 分支永远人工
- **GIVEN** "合入 master" 已自动
- **WHEN** 一个 pick 到 release 分支的 PR 具备合入条件
- **THEN** 仍生成审批，不自动合入

##### 异常：合入后 CI 变红
- **GIVEN** PR 已合入
- **WHEN** 目标分支后续构建失败并指向该合入
- **THEN** 线程出现告警，任务从终态回到进行中，收件箱出现"回滚 / 修复"选项

### S11: 每日摘要与飞书指令回流

- **触发条件**：每日固定时刻，或我在飞书私聊里回话
- **用户价值**：一天只被打扰一次看全貌；手机上回一句话就能改变任务走向（← P01, P05）
- **优先级**：P2
- **主路径**：每日固定时刻平台汇总六段式摘要（增量、判定、已做动作、待拍板、能力缺口、建议）推飞书 → 我回复"#T-200 暂停"或"T-201 pick 到 3.1"→ 平台解析并回流到对应线程执行 → 飞书回一条确认

#### 验收条件

##### 正常：每日摘要
- **GIVEN** 平台运行一天
- **WHEN** 到达 09:30
- **THEN** 飞书私聊收到摘要，包含当日新任务数、待拍板数与链接、自动执行动作数、离线 runtime 清单

##### 正常：飞书指令回流
- **GIVEN** 任务 T-200 存在
- **WHEN** 我在飞书回复"T-200 暂停"
- **THEN** 1 分钟内 T-200 状态变为暂停，线程记录"来自飞书的指令"，飞书回复确认

##### 异常：指令无法解析
- **GIVEN** 我在飞书回复一句无法对应任务的话
- **WHEN** 平台解析失败
- **THEN** 飞书回复"未识别，请用 T-编号 开头"，不执行任何动作

- **WHEN** 我打开状态视图

## 五、约束与边界

### 5.1 技术约束

- **计费**：Claude Code 与 Codex 全部走月订阅，不使用 API key。Claude 会话必须以 `claude --bg` / `--bg --resume` 启动与续接（官方文档确认后台会话消耗订阅额度），不使用 `claude -p`。Codex 用 `codex exec` / `codex exec resume`。
- **Agent 契约**：统一为四个动作：启动会话、追加消息、查询状态、读取结果。状态来源为 `claude agents --json`、Notification 钩子、Codex 会话记录。
- **网络拓扑**：开发机 10.26.20.3 无法主动连接中心机 172.17.2.13（172.17/16 被其 docker0 占用），中心机需以 `ssh -R` 反向隧道让开发机 worker 拨 localhost。笔记本可直连。Jira 只能经 VPN 访问，Jira 轮询必须调度到具备 VPN 能力的 runtime。
- **飞书**：使用现有 lark-cli 应用（`cli_a94d…`）。守护进程用机器人身份（事件订阅、发私聊、读 reaction）；用户身份 token 会过期，仅在需要读机器人不在的群时手动刷新。
- **中心机**：macOS，Postgres 17 已在运行，出网需经本机 sing-box 代理（10809）。
- **现有 skill**：jira-watch、pr-fleet-watch、pr-watch、pick-pr、teamcity、create-doris-pr、fix-pr-pipeline、gh-address-comments 作为 agent 能力被调用，不重写；它们的 cron 在平台接管后退役。
- **技术栈**：中心、面板、worker 均为 TypeScript；数据库 Postgres；面板沿用 Next.js 加 tRPC；IM 实时推送用 WebSocket。
- **安全**：worker 与中心之间预共享 token；各机器的凭证（gh、Jira、飞书、CLI 登录态）留在本机，平台不集中保管。

### 5.2 资源与时间约束

- 单人开发，AI 辅助；第一版只覆盖 M1（S01–S07）。
- 额度：每家 agent 默认并发 3；额度耗尽排队，仅分析类任务允许换家。
- 平台自身的 LLM 需求（调度员、候选扫描、分流）同样走订阅 CLI，因此要控制频次：调度员会话按需拉起、空闲 30 分钟回收；候选扫描默认每小时一轮。

### 5.3 "不做"清单

- 不做多用户、权限、租户。
- 不做 qoder 接入（无 CLI），不做多账号调度。
- 不扫描、不归类我手动开启的 Claude Code / Codex 会话。
- 不把 IM 对话镜像到飞书；飞书只收待拍板项与每日摘要。
- 不与 OpenClaw、Hermes 集成或替换它们。
- 不接入 litefuse tracing（第二阶段）。
- 不做"相似历史需求"检索（第一版无历史数据）。
- 不自动合入 release 分支，不自动把 Jira 流转到"完成"。
- 不自动创建 pick 目标，pick 的仓库与分支始终由我指定。
- 不做 UI 原型；"原型"定义为可运行的 demo 分支加一页说明。
- 不重写现有 skill 的逻辑，只调用。
